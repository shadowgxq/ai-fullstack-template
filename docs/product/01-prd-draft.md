# AI 智能衣柜系统｜产品需求文档

**状态：产品评审稿（未发布）**

## 1. 产品概述

### 1.1 产品定位与用户问题

AI 智能衣柜是一款面向个人用户的**微信小程序**。用户可以整理和管理自己的衣物，根据已有衣柜、当天城市天气、穿搭偏好及实际穿着历史获得 AI 搭配建议，并回顾已记录的穿着情况。

产品聚焦三个日常问题：**衣物多但不易查找、出门前不知道如何搭配、难以了解已有衣物的使用情况**。当前优先降低衣物录入和获取建议的门槛，不要求用户先完善全部衣物属性或积累穿着历史。

### 1.2 目标用户与使用场景

目标用户是希望整理个人衣柜、需要日常穿搭参考的微信用户。每个账户只管理自己的衣柜，不涉及家庭共享和团队协作。

| 场景 | 用户期望 |
| --- | --- |
| 整理衣柜 | 快速录入衣物，随时查找、修改和管理可穿状态 |
| 日常出门 | 结合天气、场合和偏好，获得基于现有衣物的搭配建议 |
| 穿着回顾 | 记录实际穿过的衣物，查看历史、衣物使用次数与近期趋势 |

### 1.3 产品目标

核心目标是建立一个真实可用的闭环：**录入衣物 → 获取建议 → 确认实际穿着 → 查看历史与统计 → 为后续建议提供参考**。

产品试用后主要观察首件衣物录入完成情况、有效推荐完成情况、穿着记录使用情况和用户是否再次使用。指标用于判断产品价值，暂不设缺乏数据依据的目标百分比。

## 2. 产品范围与核心流程

### 2.1 功能范围

- **账户与设置**：微信登录、可选个人资料、穿搭偏好、城市及退出登录。
- **衣柜管理**：手动录入、查看、编辑、筛选衣物，管理可穿状态及归档。
- **AI 穿搭**：参考本人可穿库存、偏好、天气和已记录穿着生成建议；支持换整套和替换单品。
- **穿着记录**：确认实际穿着、补录、查看、修改和删除误记录。
- **衣柜统计**：衣物数量、类别分布、已记录穿着次数和近期趋势。

**不在当前范围**：图片 AI 自动识别与分类、推荐喜欢/不喜欢反馈、虚拟试衣、3D 建模、自动检测真实穿着、电商导购、社交分享、衣柜共享、多用户协作、私有模型训练，以及独立 Web/PC 衣柜页面。

### 2.2 核心使用流程

1. 用户通过微信登录，进入自己的衣柜；首次使用可直接添加衣物。
2. 用户可以按需补充衣物属性、设置长期偏好或调整天气城市，均不是获得首次推荐的前置条件。
3. 用户进入穿搭页，选择当次场景，获取真实库存内的搭配建议，并可调整组合。
4. 用户**确认实际穿过**后，才保存为穿着记录；也可以以后自行补录。
5. 用户在记录页回顾穿着历史、修改误记录并查看统计；新记录可为后续推荐提供参考。

用户也可以只管理衣柜或直接记录实际穿着，不必每次按完整流程操作。

### 2.3 页面组织

主导航采用**「衣柜 / 穿搭 / 记录」**三个入口：

| 入口 | 主要内容 |
| --- | --- |
| 衣柜 | 衣物列表、筛选、状态概览及衣物录入；进入详情后可编辑、归档或恢复 |
| 穿搭 | 天气、当次场景、AI 搭配、推荐理由、换整套、替换单品及确认穿着 |
| 记录 | 实际穿着历史、补录和修改入口、统计入口 |

**个人页**通过主页面入口进入，管理资料、长期穿搭偏好、默认城市和退出登录。长期偏好与单次场景分开；完整穿着历史和统计不重复放在穿搭首页。

## 3. 功能需求

### 3.1 登录与个人设置

- 用户使用微信身份登录，不要求填写用户名、密码或手机号。首次成功登录建立个人账户；再次使用相同微信身份可访问原有衣柜。
- 登录失败或取消时可重试，不能显示已登录状态或访问个人衣柜。
- 头像和昵称可自愿填写；未填写时显示默认头像及“衣柜用户”，不影响其他功能。微信登录不代表自动取得头像、昵称或定位授权。
- 用户可以在个人页修改资料、长期偏好和城市。穿着日期与统计统一按北京时间 **Asia/Shanghai** 计算，不提供手动时区设置，也不随设备时区或所选城市改变。
- 退出登录后，不再展示当前账户的个人数据；退出不会删除衣物和穿着记录。
- 未登录进入业务页面、登录失效或退出后，直接进入微信登录页，不停留在业务页面展示登录提示；登录成功进入本人衣柜。

### 3.2 衣物录入与管理

**录入**

- 支持手动添加衣物的**照片、名称、主类别、主要颜色、适用季节或温度、场合或正式程度、标签及备注**。照片或非空白名称至少有一项，其余属性可以不填；未填写的信息保持未知，不自动补为事实。
- 为便于快速录入，优先展示照片、名称、类别和颜色；其他信息可展开填写，也允许保存后再补充。收起附加信息时保留已填写内容。
- 支持一张衣物主照片，可拍照或从相册选择，并支持更换或移除；照片须上传成功后才视为有效。不根据照片自动识别类别、颜色或风格。
- 类别和颜色可选择或清除；季节、场合和标签支持多选，标签可自定义。允许用户录入相似或重复衣物，不自动去重。
- 照片和名称都缺失时提示补充，不创建空白衣物。上传或保存失败时保留已填内容供重试；成功后衣柜展示与保存一致的信息。

**管理**

- 用户可以浏览衣物、查看详情、修改属性，并按类别及已填写属性筛选。未填写属性不能当作已知筛选值。
- 衣物状态包括**可穿、暂不可穿、已归档**。新衣物默认为可穿；只有可穿衣物参与新的穿搭推荐。
- 用户可以调整状态、归档和恢复衣物。不提供普通衣物永久删除操作。
- 编辑衣物后，衣柜及后续推荐使用最新信息；归档、改名或修改类别，不应改变已发生的穿着记录所保留的当时信息。
- 空衣柜时引导录入；筛选无结果时提供清除筛选的方式。

### 3.3 穿搭偏好

- 用户可以设置**喜欢和避免的风格、颜色、场合**，以及可选的舒适度偏好。未设置偏好不妨碍使用推荐，也不能被描述成已掌握用户喜好。
- **风格、颜色、场合的结构化避免项是硬约束，优先于喜欢项**。当某件衣物的已知属性与避免项冲突时，不能推荐该衣物；喜欢项只影响符合条件的候选排序。
- 舒适度自由文本仅作为 AI 的补充参考，不自动转换为可保证满足的排除条件。页面明确说明这一边界；未记录的鞋跟、版型等属性仍为未知，不能宣称已验证文本要求或保证舒适效果。
- 对与避免条件直接相关、但衣物尚未填写的属性，不能猜测其符合要求。系统应先使用能够确认不冲突的候选；若没有足够候选，应说明缺少哪些信息，并引导补充衣物属性或由用户主动调整条件，不能自动放宽避免项。
- 衣物风格的判断以用户已填写的相关标签等明确资料为依据；未明确记录时不宣称该衣物具有某种风格。
- 用户可在穿搭页临时选择**通勤、休闲、约会或不限场景**。临时场景仅作用于当前推荐，不修改个人页保存的长期偏好。

### 3.4 AI 穿搭建议

**推荐内容**

- AI 只能从当前用户衣柜中**可穿**的真实衣物选择，结合已填写属性、长期偏好、当次场景、可用天气和已确认的穿着历史提供建议。
- 不要求衣柜必须有固定品类，也不固定推荐套数。衣柜仅有上装等少量库存时，仍可根据已知信息提供**局部搭配建议**，但必须明确其不完整，不能虚构下装、鞋履或其他衣物。
- 历史为空、偏好为空或普通属性缺失时，仍尽可能利用有效信息给出建议；不得编造用户喜好、穿着历史、衣物属性或天气。
- 推荐理由应能解释所选衣物与天气、风格、颜色、场景或近期重复情况的关系。有多种因素取舍时，说明取舍，不承诺推荐一定适合用户。

**城市与天气**

- 未设置城市时默认使用**杭州**，并标明这是默认城市；若用户已经保存城市，则优先使用保存值。
- 用户可以主动定位或手动选择城市；不主动弹出定位授权。定位被拒绝或失败时保留当前有效城市，仍允许手动选择。
- 天气展示对应城市、日期和更新时间。天气获取失败时明确说明缺失，仍可提供不依赖天气的建议，不展示虚构的气温或天气适配理由。

**查看与调整**

- 穿搭页展示推荐的具体衣物和选择理由，重要依据及信息缺失说明默认可见。
- 用户点击**「换一套」**可以请求另一组搭配；点击单件衣物可从本人可穿库存选择替换，其他已选衣物保留。调整后仍需遵守避免条件，并更新不再成立的推荐理由。
- 没有可替换衣物时说明原因；无可穿库存时引导添加衣物；有库存但无法满足避免条件时，解释限制并提供可操作的调整建议。
- 推荐生成中提供可见的取消操作。取消后如实显示该次请求的结果：确已取消则不展示为生成成功；若取消前已经完成，则仍可查看已生成的建议。
- 生成、换整套、替换单品和取消推荐**都不会自动写入穿着历史**。AI 服务失败时明确提示并支持重新请求，不能展示虚假的成功结果。

### 3.5 实际穿着记录

- 用户可确认推荐中的衣物已经实际穿过，也可自行选择本人已有衣物补录。每条记录包含**穿着日期和一组衣物**；确认前允许调整日期和衣物。
- 只有用户主动保存的实际穿着记录进入历史。仅获取、查看或调整推荐，不代表已经穿过。
- 日期统一按北京时间 **Asia/Shanghai** 计算。允许补录过去日期和当天记录，禁止记录未来日期；同一天可记录多条真实穿搭。
- 同一件衣物在同一条记录中只出现并计数一次；若在不同记录中实际穿过，则分别计数。同一次保存重复提交不得生成重复记录。
- 用户可查看、修改或删除误记录。衣物当前已归档或暂不可穿，不影响其过去已发生的穿着事实；历史保留当时的衣物名称和类别。
- 保存失败时保留本次输入供重试；修改或删除后，相关历史和统计同步反映正确结果。

### 3.6 衣柜与穿着统计

统计只基于**当前衣柜数据及用户确认过的实际穿着记录**，并清楚区分库存与历史。

| 指标 | 统计口径 |
| --- | --- |
| 衣物总数 | 可穿与暂不可穿衣物之和；已归档数量单独展示 |
| 类别分布 | 按衣物总数范围内的类别统计；未填写类别单列“未分类” |
| 穿搭次数 | 已保存的实际穿着记录条数 |
| 单件衣物穿着次数 | 包含该衣物的有效穿着记录条数；同一记录只计一次 |
| 使用趋势 | 默认最近 30 个自然日（含当天）的穿着记录数量，可按周汇总，日期按北京时间划分 |

- 已归档衣物不进入当前衣物总数，但其已有穿着记录仍保留在历史和穿着统计中。
- 新增、修改、删除穿着记录后，所有相关统计均以最新有效事实为准。
- 没有穿着记录时显示**「暂无已记录穿着」**等客观提示；不能据此声称用户“从未穿过”。统计应标明覆盖的时间范围。

## 4. 通用产品要求

- **个人数据保护**：衣物、照片、偏好和穿着记录均归当前登录账户所有，默认不公开。未登录或退出后不得访问个人数据，其他账户不能读取或修改。
- **数据真实一致**：已确认穿着是穿着统计的唯一事实来源；归档和编辑衣物不改写过去的穿着事实。需要保存的用户操作只有真正成功后才显示完成；同次重复提交不能造成重复写入。
- **异常可恢复**：登录、选图、上传、保存、定位、天气和 AI 推荐失败时，向用户反馈真实状态；可恢复的失败不应清空用户未保存的有效输入。天气和 AI 异常不能阻塞与其无关的衣柜管理及历史查看。
- **推荐可信**：推荐不得引用其他用户、暂不可穿或已归档的衣物，不得静默忽略结构化避免项，不得将未知属性表述为确定事实。舒适度文本仅供参考，推荐不保证实际舒适度或穿着效果。

## 5. 可观察验收标准

以下验收对应正文中的产品规则；页面布局、固定区域、键盘和安全区同时遵循[业务 UI 规范](../../miniprogram/design/wardrobe-ui-spec.md)。

| ID | 前置与操作 | 可观察结果 | 对应需求 |
| --- | --- | --- | --- |
| AC-001 | 提供照片或非空白名称，其他属性留空后保存 | 保存成功后可查到与输入一致的衣物，未填属性保持未知 | §3.2 |
| AC-002 | 编辑衣物名称、类别或其他属性，再查看衣柜与历史 | 衣柜和后续推荐使用新属性，历史保留当时名称和类别 | §3.2、§3.5 |
| AC-003 | 获取或查看推荐，未确认实际穿着 | 穿着历史和次数不变 | §3.4、§3.5 |
| AC-004 | 保存实际穿着并重复提交同次操作 | 只生成一条对应日期和衣物的记录，同件衣物在记录内只计一次 | §3.5 |
| AC-005 | 修改或删除误记录 | 历史、穿搭数及单件次数反映修正结果，无残留计数 | §3.5、§3.6 |
| AC-006 | 无历史或偏好，存在合规可穿库存且 AI 可用 | 仍能取得基于有效信息的建议，不虚构历史或喜好 | §3.3、§3.4 |
| AC-007 | 库存含暂不可穿和已归档衣物 | 推荐排除这些衣物；归档保留已有历史与穿着统计 | §3.2、§3.4、§3.6 |
| AC-008 | 天气获取失败后请求推荐 | 明确天气缺失，仍可获得不依赖天气的建议，无虚构天气理由 | §3.4 |
| AC-009 | 可穿库存只有上装 | 可提供局部建议，明确不完整，不编造其他品类 | §3.4 |
| AC-010 | 其他账户或未登录用户尝试访问个人资源 | 衣物、照片、偏好、记录及推荐不被读取或修改 | §4 |
| AC-011 | 无穿着记录时查看统计 | 衣物数量仍正确，显示暂无已记录穿着，不声称从未穿过 | §3.6 |
| AC-012 | AI 服务失败，或生成中主动取消推荐 | 可见取消入口，按实际终态反馈；已取消不展示为成功，已完成仍可查看建议；不写穿着记录或修改衣物数据，失败可重新请求 | §3.4、§4 |
| AC-013 | 保存偏好后再次请求推荐 | 使用已保存偏好，结构化避免项严格执行；舒适度文本仅作参考并明确说明，不保证文本要求；无合规候选时解释原因，不自行放宽条件 | §3.3 |
| AC-014 | 未设置城市，或定位失败、被拒绝 | 无已存城市时显示默认杭州；定位失败保留有效城市，可手动选择 | §3.4 |
| AC-015 | 主动定位成功且天气可用 | 使用对应城市天气，显示城市、日期和更新时间 | §3.4 |
| AC-016 | 衣物或穿着记录保存失败后重试 | 反馈失败并保留输入，重试成功不重复写入 | §3.2、§3.5、§4 |
| AC-017 | 补录过去日期、同日多套并尝试未来日期 | 统一按北京时间判定日期，允许过去与当天及同日多套，拒绝未来日期 | §3.5 |
| AC-018 | 库存包含三种状态及未分类衣物 | 总数仅含可穿与暂不可穿，归档单列，未分类数量正确 | §3.6 |
| AC-019 | 切换当次场景、换整套或替换单品 | 当前条件或组合更新，单品替换保留其他衣物，长期偏好和历史不被误改 | §3.3、§3.4 |
| AC-020 | 使用主导航、表单和记录入口 | 衣柜、穿搭、记录三个主入口可达；记录内进入统计；固定区域不遮挡内容，键盘操作符合业务 UI 规范 | §2.3、§3.2、§3.5 |
| AC-021 | 无照片且名称为空或仅空白时保存 | 提示补充，不创建空白衣物，保留其他输入 | §3.2 |
| AC-022 | 微信登录成功、失败或取消，再退出或重新登录 | 同一身份访问原衣柜，失败可重试；退出后不展示个人数据，迟到响应不恢复旧账户内容 | §3.1、§4 |
| AC-023 | 不填头像昵称，填写多选属性和自定义标签后收起再展开 | 默认资料不阻塞使用，多选与已填内容保留，保存后与输入一致 | §3.1、§3.2 |
| AC-024 | 更换、移除主照片或清除分类与颜色 | 只保留一张主照片；清除属性后为未知；保存仍满足照片或非空白名称至少一项 | §3.2 |
| AC-025 | 避免项涉及未知属性，或衣物未明确记录风格 | 不猜测符合条件或虚构风格；优先使用可确认合规候选，不足时说明并引导主动调整 | §3.3 |
| AC-026 | 替换单品后查看理由，或校验失败、连续快速替换 | 避免条件仍有效；理由与当前组合一致，不沿用失效说明；失败保留输入，旧响应不覆盖新选择 | §3.4、§4 |
| AC-027 | 跨北京时间午夜、改变设备时区或天气城市后查看日期和趋势 | 日期口径保持北京时间；趋势覆盖含当天的最近 30 个自然日并标明范围，无手动时区入口 | §3.1、§3.5、§3.6 |
| AC-028 | 天气或 AI 不可用时管理衣柜、查看历史 | 相关独立功能仍可使用，不因推荐依赖失败被阻塞 | §4 |
