# 团队小站：产品需求文档

- 需求 ID：REQ-TEAM-TEST-001
- 需求类型：测试需求
- 文档版本：v1.0
- 文档状态：待产品与技术评审
- 产品范围：小型团队内部演示版

## 一、产品背景与目标

小团队在日常协作中，经常需要记录待办事项、发布简短通知，以及集中保存常用资料链接。目前这些内容分散在聊天消息中，不方便再次查找。

本产品提供一个轻量网页工作台，让成员打开一个地址，就能了解当前待办、查看团队公告和访问共享资料。

本次目标是交付一个可实际操作的小产品，不建设完整的项目管理平台。核心价值是：信息集中、操作简单、保存可靠、状态清楚。

## 二、使用对象与使用场景

产品面向一个小团队。所有访问者进入同一个共享工作空间，拥有相同的查看和操作能力。本次不设置账号、登录或角色权限，仅使用演示数据，不作为公开互联网协作平台上线。

典型场景如下：

| 场景 | 用户希望得到的结果 |
| --- | --- |
| 工作开始前 | 快速了解还有哪些待办，以及最近发布了什么公告 |
| 临时产生工作事项 | 记录待办，完成后标记，必要时重新打开 |
| 有安排需要告知成员 | 发布一条简短公告，并能修改或删除 |
| 找到常用参考资料 | 保存链接，供其他成员随后访问 |

## 三、本次产品范围

产品包含四个功能区域：**待办事项、团队公告、共享资料、工作概览**。

待办、公告和资料分别拥有自己的列表与操作入口；概览只汇总信息和提供跳转，不承担内容编辑。

本次不包含成员管理、任务负责人、截止日期、标签、附件上传、富文本、评论、消息推送、全文搜索、回收站、数据导出或移动端专门适配。暂不要求离线操作、实时更新或多人同时编辑同一条内容。

## 四、通用产品规则

### G-01 共享与保存

所有已经交付的功能操作同一个团队空间。操作成功后，刷新页面或关闭后重新打开，已经保存的内容仍然存在。

在浏览器 A 保存成功的内容，浏览器 B 重新打开或刷新对应页面后，应当能够看到。不能仅在创建者当前页面中显示。

本次验收采用先后操作，不要求不同浏览器之间自动实时刷新。

### G-02 输入规则

必填文本不能只包含空格。文本保存前忽略首尾空格；正文内部的换行应保留。超出字段长度限制时，应指出具体字段的问题，不允许静默截断。

相同标题可以重复创建，不能因为标题相同而覆盖已有记录。共享资料允许保存相同链接，本次不提供自动去重。

### G-03 操作反馈

保存、状态切换和删除操作必须提供明确反馈。操作进行中应避免用户对同一次动作重复提交。

保存失败时不显示成功，保留已经填写的内容并允许重试；状态切换失败时不能继续显示一个被误认为已经保存的状态；删除失败时不能把内容当作已经删除。

列表加载失败时，应显示可理解的错误提示和重试入口，不能伪装成“暂无内容”。

### G-04 删除规则

删除前必须进行二次确认，说明删除的对象以及不可恢复。取消后不改变数据，确认且删除成功后才移除该内容。

本次使用直接删除，不提供回收站或恢复功能。

### G-05 时间与排序

公告和资料显示创建时间，统一以北京时间展示，精确到分钟。未特别说明的最新列表按创建时间从新到旧排列；修改内容不改变创建时间和排序位置。

创建时间相同时应保持稳定顺序，反复刷新不能随机换位。

## 五、功能需求

### 5.1 待办事项

用户可以记录团队待办，并区分未完成和已完成事项。

| 编号 | 产品要求 |
| --- | --- |
| T-01 新增待办 | 用户填写标题后创建待办。标题必填，长度为 1–80 个字符；新待办默认未完成。 |
| T-02 查看列表 | 提供“未完成”和“已完成”两个视图，默认进入未完成视图。每个视图显示对应数量，事项按创建时间从新到旧排列。 |
| T-03 修改状态 | 未完成事项可以标记完成；已完成事项可以重新打开。操作成功后，事项移动到对应视图，两个视图的数量同步变化。 |
| T-04 删除事项 | 两种状态的事项均可删除，遵循通用删除规则。 |
| T-05 空状态 | 未完成列表为空时显示“暂无待办，可以添加一条”；已完成列表为空时显示“还没有已完成的事项”。新增入口始终可见。 |

列表只展示标题、状态及必要操作，不增加负责人、优先级或日期信息。标题较长时允许换行，不能遮挡操作按钮。

本次不提供标题编辑；需要纠正标题时可以删除后重新创建。

### 5.2 团队公告

用户可以发布、阅读、修改和删除简短团队公告。

| 编号 | 产品要求 |
| --- | --- |
| N-01 发布公告 | 标题和正文均必填。标题长度为 1–60 个字符，正文长度为 1–500 个字符。发布成功后出现在列表顶部。 |
| N-02 阅读公告 | 按创建时间从新到旧展示标题、完整正文和创建时间；保留正文换行，不支持图片或富文本。 |
| N-03 编辑公告 | 可以修改标题与正文。取消编辑不改变原内容；保存成功后展示新内容，创建时间与排序位置保持不变。 |
| N-04 删除公告 | 遵循通用删除规则。 |
| N-05 空状态 | 没有公告时显示“暂无公告，发布第一条团队通知”，并提供发布入口。 |

公告的发布和阅读不依赖待办数量，也不依赖共享资料是否存在。

### 5.3 共享资料

用户可以集中保存团队常用的网址，不必反复翻找聊天消息。

| 编号 | 产品要求 |
| --- | --- |
| L-01 新增资料 | 填写名称、网址和可选说明。名称必填，长度为 1–60 个字符；说明最多 120 个字符；网址必填且最多 2,048 个字符。 |
| L-02 网址有效性 | 只接受包含主机名的完整 HTTP 或 HTTPS 地址。缺少协议、明显无效地址或其他协议应显示错误，不允许保存。无需检查远端网站当前是否可访问。 |
| L-03 查看与访问 | 列表展示名称、网址、说明和创建时间，按创建时间从新到旧排列。提供明确的“打开资料”操作，在新标签页访问，不离开当前工作台。 |
| L-04 编辑与删除 | 可以修改名称、网址和说明；取消编辑不改变原记录。删除遵循通用规则，编辑不改变创建时间和排序位置。 |
| L-05 空状态 | 没有资料时显示“暂无共享资料，可以添加常用链接”，并提供新增入口。 |

长网址不能撑破页面或遮挡操作。可以缩略显示，但用户应能方便地查看完整地址。

资料管理不依赖公告的发布，也不依赖待办是否完成。

### 5.4 工作概览

当待办、公告和资料均已提供后，用户可以在概览中快速了解团队空间的当前情况。

| 编号 | 产品要求 |
| --- | --- |
| O-01 数量摘要 | 显示“未完成待办”“团队公告”“共享资料”三个数量。公告与资料统计当前仍存在的全部记录；待办只统计未完成事项。 |
| O-02 待办摘要 | 展示最新创建的最多 5 条未完成事项。只提供阅读和进入待办页面的入口，不在概览直接修改状态。 |
| O-03 公告与资料摘要 | 分别展示最新创建的最多 3 条公告、最多 3 条资料。公告展示标题与创建时间；资料展示名称与创建时间。 |
| O-04 导航 | 各摘要区有清晰的“查看全部”入口，分别进入对应功能页面。 |
| O-05 数据一致性 | 用户在其他功能页成功新增、编辑、删除或改变状态后，再进入或刷新概览，应展示最新的数量和摘要；已经删除的内容不能继续出现。 |
| O-06 空数据与失败 | 某类内容为空时，该区域显示简短空状态，其他区域正常展示。某类数据加载失败时显示错误与重试入口，不把失败显示成数量 0，并保留其他成功加载的区域。 |

概览不展示趋势图、完成率、绩效评分或其他额外统计。

## 六、页面与交互要求

### U-01 页面结构

产品采用统一、简洁的顶部导航，名称使用“工作概览”“待办事项”“团队公告”“共享资料”。只展示已经交付且可用的功能入口，不展示占位页面、不可点击入口或“开发中”的功能卡片。

待办版本先交付时，默认进入待办页面；概览交付后，默认进入概览。任何已开放页面都应能通过顶部导航返回其他已开放页面。

### U-02 视觉风格

面向桌面浏览器，以 1440 × 900 作为主要验收尺寸，1280 像素及以上宽度也应可正常使用。页面内容居中，保留适当留白；不出现页面级横向滚动条，内容较多时可以正常向下滚动。

使用浅色背景、清晰文字和克制的强调色。同类按钮、输入框、列表、空状态和错误提示保持一致。正文建议不小于 14 像素，状态不能仅依赖颜色区分。

不添加营销横幅、装饰性大插画、多层侧边栏或与本次功能无关的图表。界面首先应便于阅读和操作，而不是填满屏幕。

### U-03 表单与确认

新增和编辑使用样式一致的弹窗。必填项和长度限制清楚，错误提示靠近对应字段；取消操作不保存数据。

弹窗应能通过键盘操作，不能遮挡自己的提交、取消或关闭按钮。删除确认应明确显示被删除内容的名称，不能只显示没有对象信息的“确定删除吗”。

### U-04 状态完整性

每个已经交付的功能必须同时提供正常、加载、空数据、输入错误和操作失败状态。不能只交付理想数据下的页面。

UI 验收以实际可操作页面为准。代表性页面的布局和视觉方向应先确认，再扩展到其他功能；不以“功能能点击”代替视觉与交互验收。

## 七、功能独立性与交付要求

待办事项应当能够先独立投入使用，不能等待公告、资料或概览完成后才可用。

公告和共享资料可以在待办可用版本之后分别加入，两者没有先后依赖。先提供其中任意一项时，已经交付的功能仍应完整可用。

概览可以最后提供。在概览尚未提供时，不能影响待办、公告和资料的独立使用。

每次增加功能都必须保持原有已交付功能的行为和已保存数据，不得要求清空历史数据才能使用新功能。不能因为其他功能尚未交付，给当前功能增加无法完成的操作路径。

## 八、代表性验收场景

以下场景用于验证实际产品，不替代前述完整要求。所有测试内容均为演示数据。

| 编号 | 操作与预期 |
| --- | --- |
| A-01 待办闭环 | 创建“整理周会纪要”和“确认首页文案”，将第二条标记完成。未完成视图为 1 条，已完成视图为 1 条。重新打开第二条后，数量变为 2 和 0。 |
| A-02 公告闭环 | 发布标题为“本周发布安排”的公告，正文包含两行文字；阅读时保留换行。修改正文并保存后展示新内容，原创建时间不变。 |
| A-03 资料闭环 | 保存名称为“设计参考”、网址为 `https://example.com/design` 的资料；点击打开后在新标签页访问。无需以示例网站是否返回有效页面判断保存功能是否通过。 |
| A-04 输入校验 | 空白待办标题、超过 60 个字符的公告标题，以及未带协议的资料网址均不能成功保存；显示字段错误，其他已填内容不丢失。 |
| A-05 删除确认 | 对任意已有内容发起删除，取消后内容仍存在；再次发起并确认，成功后内容消失，刷新后也不再出现。 |
| A-06 共享保存 | 浏览器 A 创建内容并收到成功反馈；浏览器 B 重新打开对应页面，应看到同一条内容。随后在 A 删除成功，B 刷新后不再看到它。 |
| A-07 概览汇总 | 在一个只包含 1 条未完成待办、1 条已完成待办、1 条公告和 1 条资料的空间中，概览三个数量依次为 1、1、1。将未完成待办标记完成，再进入概览，未完成数量应为 0。 |
| A-08 摘要上限 | 当存在 6 条未完成待办、4 条公告和 4 条资料时，概览分别展示最新 5、3、3 条；数量摘要仍反映全部符合条件的记录，而不是摘要行数。 |
| A-09 失败恢复 | 在服务暂时不可用的情况下尝试保存，不出现成功提示，输入保留且可重试。列表读取失败时显示错误而不是空列表；恢复后重试可以正常加载。 |
| A-10 独立交付与界面 | 只有待办功能时，页面仍能完整使用且没有其他功能的空入口。后续加入公告或资料，不破坏原有操作和数据；在主要验收尺寸下没有内容遮挡或横向溢出。 |

## 九、完成标准

本次范围内的功能与通用规则全部满足，核心操作在实际运行页面中可完成；保存与共享结果可验证，异常反馈清楚，视觉与交互符合已确认方向。

验收不得依赖预置假数据代替真实新增、修改和删除结果。没有尚未处理的阻塞缺陷；不在本次范围的优化建议可以单独记录，不因此无限扩大本次交付范围。
