# AI 智能衣柜 V2｜天气穿搭与穿着日历

**状态：V2 PRD 评审稿；核心范围已确认，交互细节供评审，尚未进入设计与实现阶段。** 面向产品、设计与研发。本文是本批 V2 的唯一需求来源；推荐来源、城市更新、日历入口和轻量记录按本文定义，其他规则沿用 [基础产品需求](01-prd-draft.md)。

## 1. 概述

V2 面向 20–30 岁的男性和女性，优先解决新用户尚未录入衣物、无法立即获得穿搭价值的问题。用户无需先建好衣柜，即可按城市天气和出行场景获得穿搭参考；随着衣物录入，进一步使用本人衣柜的真实搭配。

首次使用直接获取默认城市杭州的真实天气并提供穿搭参考，不要求先选城市或授权定位。定位成功后可引导用户切换到所在城市。穿着日历承接按天回顾和补录；定时任务可用于提前准备穿搭建议，天气获取和城市更新独立于任务执行，主动通知作为独立可选能力。

## 2. 背景

现有产品基准要求推荐从本人可穿衣物中选择，无库存时引导添加衣物；穿着记录必须关联已有衣物。这个流程使尚未录衣的新用户先付出整理成本，才能体验核心推荐价值。

V2 将“获取穿搭参考”提前到录衣之前，同时区分通用品类建议和真实库存搭配。日历用于建立持续记录和回顾习惯；空日历不能承担新用户首次体验的主要价值。

## 3. 目标与衡量

**首要目标：新用户不录衣，也能获得有用、能理解、可照着搭配的建议。** 次要目标是帮助用户按日期记录与回顾实际穿搭。

建议在首轮试用的前两周观察以下指标；观察周期为评审建议，不预设无依据的增长目标：

| 指标 | 口径 |
| --- | --- |
| 空衣柜首次建议完成率 | 进入推荐入口时衣柜为空、且成功看到完整穿搭参考的新用户数 / 进入该入口的空衣柜新用户数 |
| 建议可用性 | 试用访谈中，用户能否理解搭配理由、并从现实拥有的衣服中找到可执行组合；分别覆盖男性和女性用户 |
| 7 日再次使用率 | 首次看到建议后 7 日内再次查看建议或保存实际穿着的用户数 / 已满观察窗口的首次建议用户数 |

天气缺失时的通用建议单独观察，不算作成功提供天气适配建议。访谈和试用结果用于设定下一轮目标，不在本期额外增加评分、点赞系统。

## 4. 用户群体

| 群体 | 主要需求与限制 |
| --- | --- |
| 20–30 岁、尚未录衣或录入较少的男性与女性 | 出门前快速决定怎么穿，不愿先花大量时间整理衣柜；这是首发重点 |
| 同年龄段、开始持续管理衣柜和记录穿搭的用户 | 根据实际衣物搭配，按日期找回穿过的组合，减少重复决策 |

年龄用于产品定位，不要求填写出生日期，也不以年龄阻止其他用户使用。男装、女装或不限方向由用户主动选择，不从头像、昵称、照片或定位推断。

## 5. 价值主张

| 要素 | 尚未录衣的用户 | 持续使用衣柜的用户 |
| --- | --- | --- |
| Who：谁 | 希望直接获得帮助的新用户 | 已开始积累衣物和穿着记录的用户 |
| Why：要完成什么 | 根据天气和场景决定今天怎么穿 | 快速选搭配，并找回某天的实际穿着 |
| What before：目前怎么办 | 假设主要查看天气、凭经验或搜索穿搭内容，需自行判断适用性 | 通过记录列表查找，或自行翻相册回忆 |
| How：怎样提供帮助 | 无需录衣，给出可执行的品类组合、层次和理由 | 衣柜搭配与按日历查看、补录形成连续路径 |
| What after：获得什么 | 首次使用即有参考，再逐步录入衣物 | 更容易复用过去的搭配，持续积累真实记录 |
| Alternatives：替代方式 | 天气应用、社交平台穿搭内容；本产品减少重新搜索和判断天气适用性的步骤 | 相册、备忘录、普通日历；本产品可连接衣柜与穿着事实 |

价值主张：先帮助用户解决“今天怎么穿”，再帮助他们建立自己的衣柜。天气参考与实际穿着记录相连，但查看建议不等于已经穿过。

## 6. 方案

### 6.1 核心路径

登录后进入穿搭入口 → 无已存城市时直接获取杭州天气，标注“默认城市”，无需先完成设置 → 查看当天穿搭参考 → 按需调整推荐方向、场景和偏好，或录衣、记录实际穿着。

城市更新路径：用户主动定位 → 定位到不同城市后提示“已定位到苏州，是否更新天气与穿搭建议？”（苏州为示例）→ 确认后保存城市、获取对应天气并更新建议。用户选择“暂不更新”、拒绝定位或定位失败时，保留原城市和可用内容；定位到同城无需重复确认。再次进入时优先使用用户已确认保存的城市；也保留手动选城入口，不因默认杭州而限制其他城市。

日历入口 → 自动选中最近一次有记录的穿着日期并展示对应月份与记录 → 点击其他日期切换当天内容 → 记录或补录 → 保存后展示该日穿搭，更新日期印记和月度摘要。没有任何记录时，默认本月今天，直接引导记下第一套。

主导航为「衣柜 / 穿搭 / 日历」，日历替换现有“记录”入口；统计仍从日历进入，个人仍为二级入口。此批不增加“今日”页，不调整登录后的默认落点。

### 6.2 功能与验收

| REQ-ID | 需求与可观察验收 |
| --- | --- |
| REQ-V2-001 | **无库存穿搭参考。** 空衣柜也可获得至少一套有明确品类、厚薄或叠穿方式、配色及理由的参考，注明“穿搭参考”；不生成虚假衣物 ID、不自动添加库存，不将建议表述为用户已拥有的衣物。不承诺客观最优或保证舒适。天气不可用时说明缺失，仍可提供不依赖天气的参考。 |
| REQ-V2-002 | **男女推荐与可选偏好。** 提供男装、女装、不限方向；默认不限，未选择也可使用。场景沿用现有选项；长期偏好与单次选择分开。已设置的结构化避免项继续有效，不因衣柜为空而静默忽略；无法满足时明确说明。 |
| REQ-V2-003 | **默认杭州与动态天气。** 未保存城市的用户直接使用杭州；天气内容从数据源获取，不能写死，也不要求用户从晴、雨、冷、热等固定选项中自行选择。展示城市、默认来源、天气日期及数据更新时间；进入页面按数据有效性获取或复用天气，不等待定时任务。不首次进入就索要定位，不在后台追踪位置。主动定位成功且城市不同时引导确认更新；接受后保存新城市并更新天气和建议，拒绝、取消或失败则保留原城市。同城定位不重复提示，手动换城与定位确认后的选择均可在下次进入时复用。新城市天气获取失败时说明缺失，不能将杭州天气或其建议冒充新城市结果；缺失事实不由 AI 补写。 |
| REQ-V2-004 | **每日准备建议。** 定时任务可每日按北京时间提前准备当天穿搭建议，使用当时有效的城市天气；首发具体执行时刻待评审确定。天气获取与更新独立运行，不固定为任务执行时的一份内容。进入页面早于定时准备、任务失败或尚无结果时，也能触发当日生成，并展示真实加载或失败状态。城市、推荐方向、偏好、日期或影响搭配的天气依据变化后，旧建议不冒充当前条件下的新结果，更新不等待下一次定时任务。同一条件下重复执行不造成重复展示或重复通知；任何自动生成均不写入穿着记录。 |
| REQ-V2-005 | **参考与真实库存分清。** 已有衣物用户仍可使用本人可穿库存搭配。通用品类建议与库存衣物分别标识；库存不足可展示局部搭配，并提供独立的完整穿搭参考，不能把通用建议混充本人单品。衣物归档或状态变化后不继续将旧组合显示为当前可穿推荐。 |
| REQ-V2-006 | **穿着日历。** 日历替换“记录”。首次进入默认选中最近一次有记录的穿着日期，并展示其所在月份；最近按穿着日期而非创建或修改时间判断，补录较早日期不改变该口径。同日多条按创建时间倒序展示，最近保存的一套优先；日期与内容保持一致。支持点击日期、切月、回到今天；无记录日显示该日空状态，不继续冒用最近记录。没有任何记录时默认今天。允许过去与当天、同日多套，未来日不能保存实际穿着；日期按 Asia/Shanghai 划分。 |
| REQ-V2-007 | **月度摘要。** 展示记录天数、穿搭次数、穿过的衣物数：分别为当月有有效记录的去重日期数、有效记录条数、已关联衣柜衣物的去重数量。明确统计月份；不将记录天数称为真实出勤或穿衣天数。暂不引入“搭配成片”指标。 |
| REQ-V2-008 | **无需录衣即可记录。** 每条记录包含穿着日期，可添加一张穿搭照片、文字描述和已有衣柜衣物，三者至少有一项有效；支持仅照片、仅非空文字、照片加文字及原有仅关联衣物的方式。照片支持拍照或相册、更换与移除，上传成功才算有效；未关联衣物也能保存，不强迫先建立衣柜，不自动识别照片或创建衣物。支持后续编辑和关联本人衣柜衣物。 |
| REQ-V2-009 | **打卡与事实一致。** 保存真实穿搭成功后，该穿着日期显示勾选印记；一天多条只计一个记录日，补录计入实际穿着日期。点击日期、查看建议、选图但未保存均不打卡。用“本月已记录 X 天”表达积累；删除该日最后一条记录才清除印记。未关联衣物的记录计入天数与穿搭次数，只有明确关联的衣物进入单件次数和去重衣物数，后补关联或移除关联同步重算，不重复累计。 |
| REQ-V2-010 | **记录可恢复与私有。** 保存或上传失败保留有效输入并支持重试，同次重复提交只保存一条记录；编辑失败不覆盖原记录。照片、文字和衣物关联仅本人可访问，退出后不残留上个账户内容。编辑、删除以及跨日改期同步更新日历、历史、月度摘要和原有统计；照片与文字不证明拥有某件衣柜衣物。已有仅关联衣物的记录可继续查看、编辑和统计，无需补照片或文字。 |

### 6.3 日历选择与打卡交互

- **默认与返回**：从其他主入口重新进入日历时使用最近穿着日期；从详情、编辑或记录表单返回时保留正在查看的日期。新建或改期保存成功后选中保存的日期并显示对应月份；删除后保留该日期，若已无记录则显示空状态，不突然跳走。
- **切换月份**：当前月选中今天；过去月份优先选中该月最近有记录的一天，无记录则选中该月最后一天。未来月份可浏览，但不展示可保存的打卡动作；仅提示未来日期尚不能记录实际穿着。“今天”随时回到当天及其记录或空状态。
- **选日内容**：下方标题始终显示选中日期和记录条数；有记录时先呈现最近保存的一套，其余同日记录在后，不混入其他日期。只写文字的记录用文字卡片自然展示，不生成假照片；只上传照片的记录不补造描述。关联衣物为可选信息。
- **新增入口**：今天未记录时为“记录今日穿搭”，已有记录时为“再记一套”；历史日期为“记录这一天”。记录表单默认所选日期，照片和文字在前，关联衣柜衣物为可选项。删除、更换照片或清空文字后仍须满足有效内容至少一项。
- **打卡反馈**：保存成功短暂提示“已记录这一天的穿搭”，新增记录日才增加月度天数；一天记多套不重复增加天数。主界面显示月份、记录天数、穿搭次数和有记录的日期印记，完整衣物统计通过入口查看。摘要中衣物数明确指已关联衣物；未关联不推断为真实穿衣数量。
- **加载与失败**：日期选择可立即反馈，内容区显示该日期的加载状态；失败时提供局部重试，不把失败当作无记录。快速切日后迟到结果不能覆盖当前选择，月度摘要不得只根据已加载的部分列表计算。首次最近记录定位失败时不冒充“暂无记录”。

**日历样式目标（需求层）**：让用户一眼区分今天、当前选中日期、有记录日期和未来日期；印记不能只靠颜色区分。月份与记录积累先于当日内容呈现，选日后内容对应清晰；小屏下日期易点击，记录内容和新增入口不能被固定导航遮挡。沿用产品既有视觉风格，具体配色、布局尺寸、组件和设计稿在后续设计阶段确定。本期以日历印记和累计记录天数建立打卡感，不增加积分、排行榜、强制连续签到或断签惩罚。

### 6.4 天气获取、定时准备与通知的边界

天气按当前有效城市及数据时效获取，不依赖定时任务是否执行；定时任务仅用于提前准备穿搭建议，不能替代用户进入或换城时的天气读取和建议更新。本期在小程序内查看建议，主动通知留待后续评估；如引入，须默认关闭，由用户主动选择，并核实渠道、有效授权和实际可支持频率，不预先承诺每天必达。

首次生成失败可重试；不能用昨天的建议冒充今天。内容须标明所依据天气的实际时间，不把每日更新包装成实时天气服务。定时任务的用户覆盖范围和成本控制在技术方案阶段确定，不能默认对全部历史账户每日调用模型。

### 6.5 已确认范围与验证边界

- 已确认：目标用户为 20–30 岁男性和女性；首要目标是新用户不录衣也能获得有用建议。首次无已存城市时统一用杭州，天气来自真实数据源；定位后引导确认更新，天气获取不依赖定时任务。
- 已确认：日历替换“记录”、保持三栏导航；支持不录衣直接用照片和文字记录穿搭；默认展示最近一次，点击日期切换；日历具备打卡积累感。
- 待评审的产品细节：首发照片限一张，文字和关联衣物可选，允许各自独立保存；最近按穿着日期判断，同日最近保存优先。这些是为补全流程提出的建议口径，不冒充已经逐项确认的决定。
- 技术方案须明确每日准备建议的覆盖范围、执行时刻、天气时效及失效更新策略；这些配置不能阻塞用户随时进入、读取天气并取得建议。主动通知不作为本期交付条件。
- 待验证：用户现有替代方式、建议实际可执行性，以及日历是否提高记录与再次使用。少量库存不是用户全部现实衣物，不据此推断其真实拥有情况。

## 7. 发布范围

**首发优先**：无库存天气穿搭参考、男女推荐方向、默认杭州直接提供天气、定位后引导更新城市、每日准备与进入页面时补充生成。应先在两类推荐方向和空衣柜条件下验证首用价值，同时验证无定位、定位拒绝、同城定位、跨城确认和新城市天气失败等路径。

**同批次必需范围**：日历替换记录入口、默认最近记录、按日切换、照片／文字轻量记录、可选关联衣物、打卡印记和月度摘要；保留现有记录与统计事实。日历和轻量记录一并交付，不能只换导航名称而保留必须选衣物的录入门槛。

验收至少覆盖：空衣柜获取男女方向参考；默认杭州及定位确认更新；定时任务未执行时仍能取得建议；无历史默认今天；最近记录跨月与补录旧日期；同日多套与纯文字／纯照片；切日加载失败与快速切日；保存重试不重复；删除最后一条、改期及后补衣物关联的计数同步；既有记录兼容与跨账户隔离。

**后续评估**：主动通知、未来穿搭计划、更多个性化调整。未来计划如引入，必须与已发生的实际穿着分开。

**本期不做**：五栏导航改版、AI 成片、虚拟试衣、电商导购、后台持续定位、自动确认穿过、强制采集年龄或性别。具体工期在设计和技术方案明确后评估。
