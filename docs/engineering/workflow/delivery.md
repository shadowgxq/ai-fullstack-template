# 全栈交付流程

## 适用范围与分级

本页维护项目协作规则，参考 [Manager v2 工作流](https://github.com/shadowgxq/skills/blob/9bd7ea0fe2c0d0270dbfbcd9b4fc927f6f2c0349/MANAGER-WORKFLOW.md)。**流程约定不等于自动控制已接入**：执行前先查 [工具与兼容边界](tooling.md)，不可直接将 v2 示例计划交给本仓库旧校验器。

| 工作 | 最小流程 |
|---|---|
| 探索：方向或技术可行性未定 | 调查/代表性原型 → 方向确认；不标记生产完成 |
| 小修：既定行为内的局部缺陷、文案或间距 | 复现 → 最小修改 → 针对性验证；按授权使用现有 repairs |
| 标准变更：独立可验收的功能 | 复用或补充技术方案并批准 → 当前 change → 实现 → 集成验收 |
| 高风险：权限、数据、兼容或跨系统边界 | 专项方案与人工审查 → 分步实施 → 强化验证与发布决策 |

风险按影响判断，不按代码行数。纯模板文档/导航维护可直接在 PR 记录范围和证据，不新增业务 PRD 或重复任务包；业务行为变化仍由 change 管理。同一工作只用一个执行队列，不能同时登记 repair 和 Manager bugfix。

## 一个意图，一个跨端交付单元

```text
PRD 行为与验收 → 技术总方案 / 必要专项方案 → 人工内容批准
  → 近期里程碑与垂直 change 规划 → 生成当前 change 制品 → 范围确认
  → 实现与集成 → 独立 review / 必要浏览器验收 → 里程碑产品确认
  → 单独授权的归档；合并与发布分别决定
```

需求定义 WHAT，业务技术方案定义 HOW，OpenSpec design 只写本次差异，计划定义交付边界与依赖。沿用 `docs/product/`、`docs/architecture/`、`docs/contracts/`，不因上游目录示例再建平行事实源；路径映射见 [工具入口](tooling.md#资料与状态归属)。

提取 PRD 全文中的行为、失败与数据保证，保留源位置和限定，不只读取 Acceptance 标题。每条验收明确所属 change，必须凭自身与显式依赖实现；同一个端到端意图通常包含接口、前后端、错误处理和测试，不按页面、端、Agent 或任务数量机械拆开。独立可消费 API、高风险迁移可按真实边界单独交付。

先规划当前可验收里程碑，只细化近期工作和当前 change；远期保留路线图并标明未排期，不预生成全产品四件套。规划不是实现，也不是产品验收；当前旧索引的登记时点与字段限制见 [兼容模式](tooling.md#当前兼容模式)。

## 批准、实现与证据

批准记录引用真实决策、涉及文件及内容版本；未裁决的阻塞问题不能由 Agent 填成已批准。已批准且内容未变的方案可复用，复杂/高风险偏离需重新审查。首次 UI 模式先确认代表性页面与关键状态，再扩展同类页面；已批准组件内的局部调整不重启整套方案流程。

实现前确认行为/不变量、可复用入口、状态/副作用拥有者和直接消费者。完成后按 [公共变更复核](../common/code-quality.md#变更复核) 检查 diff 与真实调用链，再按 [验证范围](../common/README.md#验证范围) 执行；不以主观风格或未测量的性能猜测强制重构。

Review 与检查针对同一代码及需求/方案/契约版本，修改后受影响证据失效。记录实际命令、退出结果、证据位置及未运行项；勾选任务、模型自评或 CI 绿灯不能替代用户验收。UI 行为/视觉变化需真实浏览器操作和批准基线对应的证据；无浏览器时明确未验收。Manager 汇总后更新 tasks，Worker 不自行宣布全局完成。

v2 自动批准绑定、gate 凭证与新鲜度校验仅在完整控制工具通过预检后使用。当前兼容模式由操作者记录并核对版本与实际证据，不伪造 receipt，不把人工记录称为自动门禁。

## 并行、Goal 与失败

外层是独立 changes，内层是一个 change 的就绪任务依赖图；一个 parallel 标记不代表两者均安全。契约先定，再按依赖安排任务；同时核对读写文件、共享 schema、锁文件、数据库、端口、缓存和浏览器会话。一个 change 只有一个制品/进度写入方，不并发启动多个完整 apply。

默认主线程或单 Worker。完整 v2 接入后，复杂 change 才按需使用 `execution.yaml` 与 claim；claim 不是文件 ACL，严格隔离另需授权 worktree/沙箱。释放运行中的 claim 或修订前必须确认原线程停止；最终检查在同一集成快照进行。没有原生派发工具不得模拟多 Agent，未经批准不静默切换执行模式。

Goal 仅驱动已批准的有限批次，每轮一个 selection；范围、轮数与停止条件固定，无进展、阻塞、预算耗尽或到达里程碑就停止。重启会话不等于新批准，也不清零修复次数。本仓库未接入这些运行控制时，不启动 v2 自动 Goal。

| 失败类型 | 处理 |
|---|---|
| 需求/设计正确，实现错误 | 只修代码与回归测试；自动修复最多两次，同一问题/版本持续计数，耗尽或无法追踪就停止 |
| 同目标下设计或需求需改 | 先分析显式依赖及共享文档/契约的隐式影响，人工确认后停止相关执行，定点修订并重新批准/验证 |
| 新目标替换旧目标 | 新建 change ID，明确替代关系与消费者；取消不等于完成，不借追加计划隐藏替换 |
| 已归档行为需改 | 新 change 引用旧基线；历史目录只读 |

不为通过检查删掉承诺的能力、篡改验收或重排无关工作。v2 取消/修订状态不能直接写进旧索引；不兼容时停止状态迁移，保留原记录和决策引用。

## 最小上下文包

[根 AGENTS](../../../AGENTS.md) → [文档地图](../../README.md) → 涉及端入口 → 当前任务 → 相关 PRD/批准方案 → 契约与直接消费者，只读任务需要的部分。代码规则通过各端编码入口加载，已读不重复；文档任务不默认加载全部代码规范、历史 PRD、日志或社区 skill。

交接保留目标、来源/批准版本、必要输入、读写范围与禁止区域、依赖和运行资源、验收与停止条件。远程输入由对应工具取得明确快照并保留源定位；未知、失效或含糊的输入不能以其他文件冒充。主线程保留决策、阻塞和证据引用，Worker 不继承全部聊天历史。

## 同一 PR 的文档同步

| 变化 | 必须同步 |
|---|---|
| 用户行为 / 验收 | 产品需求、方案/批准、change specs/tasks、受影响消费者与回归 |
| 边界 / 选型 | architecture/ADR、方案及批准有效性、依赖配置、受影响 README |
| API / DTO / 状态 / 错误 | 提供方代码、`make contracts`、语义说明、直接消费者测试 |
| 表结构 / Checkpoint 兼容 | 迁移、兼容说明、真实 PostgreSQL 验证 |
| 新组件 / 目录 | 专项组件清单或地图，不复制规范 |
| 环境变量 / 命令 | `.env.example`、README、Compose/CI |
| 完成 / 阻塞 / 修订 | tasks、当前计划与实际证据；受影响旧结果不能继续当有效结果 |

归档与剪枝只走 [显式归档](tooling.md#显式归档与剪枝)。自动检查覆盖的内容以实际脚本为准，链接通过不证明语义正确，文件 hash 不证明真实人工批准。
