# 前端初始化与上游同步

本页分别维护复制模板后的视觉初始化与前端上游代码同步。两者独立，不因复制模板、调用初始化入口或新增业务而自动同步上游。

## 复制模板后的视觉初始化

### 入口与范围

项目级 [project-init](../../../../.agents/skills/project-init/SKILL.md) 是显式执行入口，规则只维护在本节。它不安装环境、不清空数据、不更改技术架构，也不替代通用设计 Skills。

### 模式选择

仅有以下两种执行模式：

| 类型 | 名称 | 执行范围 |
|---|---|---|
| `cleanup` | 清理模板示例 | 清理获授权的模板示例、已被确认方案替代的说明及失效预览、引用；示例可位于公共库的 Examples 画板内。保留公共组件、Token、组件样式与视觉规范，不更换风格 |
| `rebuild` | 重建视觉体系 | 按新方向更新 Token、受影响组件样式、公共 Pen 及实际消费者；验证替代内容后清理被替代的旧资产，保留工程架构和交互契约 |

执行初始化时，用户未指定模式就先询问：“请选择 `cleanup`（清理模板示例，保留现有风格）或 `rebuild`（重建视觉体系）。”选择前只做只读盘点，等待回答，不默认沿用、不代选模式，也不把盘点报告为初始化完成。当前请求或同一任务上下文已明确指定类型，或以自然语言明确选择了对应模式时直接执行，不重复询问。仅分析、说明或查看状态的请求保持只读，无需选择执行模式。

例如，`$project-init cleanup，清理旧模板设计示例和关联预览，保留公共库` 选择清理模式；`$project-init rebuild，改为暖白背景、橙色强调的视觉体系` 选择重建模式。模式选择不等于授权清空目录：`cleanup` 仍需依据实际依赖明确清理对象；`rebuild` 沿用已给定方向，缺少方向时先澄清再执行依赖该方向的替换。

两种模式均按授权范围执行；展示页面代码只有在用户明确纳入范围时才清理，并同步受影响路由和导航，不删除仍需保留的路由或基础能力。只改颜色、字体等局部视觉要求按 [前端任务路径](../README.md#任务路径) 定向修改，不另设第三种模式或扩成全面重建。普通业务继续按该路径增量设计，不反复初始化。没有策略配置文件、多套长期模板分支或额外审批流程。

### 执行顺序

1. **盘点与保护**：核对工作区和未提交改动，沿 [资产登记](../../../design/README.md#资产登记)、[组件清单](../components/component-inventory.md) 与 [Token 政策](../../../design/tokens.md) 查实际 Pen 导入/实例、CSS 变量消费者、预览和当前文档引用。公共库内的主组件、必要状态与 Examples 页面分别盘点，不能把整份公共库当作待清理示例。区分模板示例与使用方真实业务，限定待改路径；涉及 Pen 操作时先确认实际工具可用。不根据文件名或目录整批删除，不覆盖无关改动。
2. **确定目标**：沿用用户已给定的新方向与保留项；方向不明确时先澄清或按授权提出方案，不擅自把“清理”解释为重新设计。已要求重建但新方向尚未确定时，只能清理明确授权且确认无依赖的模板示例/失效预览，保留可运行样式和仍被引用的库；在资产登记注明旧视觉待替换，不把旧稿当新业务的目标基线，也不宣称重建完成。仅清理示例且保留风格时不改变当前基线的有效性。
3. **先替换再清理**：重建在授权范围内更新公共库、项目 Token、组件样式及实际消费者，设计与代码按 [同步约定](../../../design/tokens.md#设计与代码同步) 保持一致。优先保留稳定的语义名、组件 API 和交互契约；确需更名时同步全部直接引用，不为兼容旧外观保留平行色板或组件。Pen 的读写、保存回读、主题表达与必要视觉确认遵循 [设计交付约定](../../../design/design-handoff.md)，不另建一套制稿流程。
4. **检查后移除**：确认替代资产、实例/变量引用和受影响画面有效后，删除已不再使用且在授权内的旧设计、预览和样式；仅清理任务也必须先核对保留内容不依赖删除对象。保留通用布局、响应式、可访问性及组件交互规则，不把所有设计/工程规范一起清空；保留真实业务、账号/权限、路由、Provider、数据、密钥和 `.git`，不清空进行中的 Manager/OpenSpec/repair 状态。按下节完成方案与引用清理，核对 Skill、README、配置和导出目录中的旧路径与失效 Frame ID；只移除确认无内容的旧目录。已结束的本地编辑回执可先移出工作区备份，不删除缓存活动写入或有效快照。
5. **验证与交接**：按 [验证范围](../../common/README.md#验证范围) 依据实际变更选检查，不按初始化名称扩大验证。非运行时变更只检查 diff；代码或设计改变时，检查直接受影响的实现、引用与画面，主题和状态检查遵循设计交付约定，不擅自启动或发布服务。分别记录实际结构、代码、运行与视觉检查，未执行项标记 `not_run`；CSS 引用或截图存在不代表渲染通过。缺工具、关键输入或有效验证时保留可恢复源与未完成项，不把文档更新当成体系替换成功。

### 方案与引用清理

- 依据已确认的替代关系和真实依赖识别失效内容。尚未实现的目标、当前能力边界与有依据的兼容路径不因暂未使用就视为无效；保留兼容时说明所支持的依赖与移除条件，不为假设依赖保留平行实现。
- 遵循 [文档维护规则](../../../README.md#文档维护规则)，在受影响的长期文档中原位重写，只描述当前方案；删除已被替代的方案、旧版本批评和变更叙述，不保留旧正文再追加纠正。当前限制、必要决策依据与来源继续保留，不能改写正确需求来掩盖实现偏差。
- 同步资产登记、组件定位、视觉规范、Token 政策及直接引用；代码已纳入授权时，一并更新调用方，移除过时实现、配置、导出和引用，并同步相关测试与文档。移除旧行为前核对调用方、公共契约和持久化数据需要，不扩成无关清理。
- 将长期现状正文与正式归档、验收证据分开处理。保留仍有审计或依赖用途的 ADR、已封存 OpenSpec 和验收记录，不重写历史；长期正文中的过时方案说明不因“保留历史”而继续保留。

### 完成边界

当前设计文件与内容以 [资产登记](../../../design/README.md#资产登记) 为准。初始化不要求存在业务设计稿：没有时直接跳过其清理，不创建占位稿、不将其缺失报告为失败，也不删除公共库来满足清理目标。复制后的业务项目出现真实需求时，再按需建立业务消费稿并正式导入公共库；不为每次需求新增 Pen 文件，也不为目录齐全扩建组件。

只有范围内的旧资产、已替代方案正文与直接引用都已核对处理，才能报告清理完成；旧路径搜索无匹配只证明路径检查，不能代替方案内容复核。有未解决依赖时保留并说明缺项。

初始化结果只记录在当前回复或已有 PR/change；重复调用时回读实际资产；未明确要求再次更换时只补未完成部分，不重置已建立的项目风格。需要的新视觉确认沿用已有设计流程，不增加独立 MD 审批或逐组件签字；没有业务需求时不编造 PRD 或业务代表页。

初始化结束后返回原协调者，后续业务仍由 `ui-ux-delivery` 读取当前项目规范并交付设计，再进入技术方案与实现。初始化接受只覆盖实际公共基线，不代替业务代表页确认或最终产品验收；仅请求初始化不自动开始整套业务开发。

## 上游代码同步

仅在明确要求集成或同步上游前端时执行以下内容；视觉初始化不触发来源代码覆盖。

从标准 frontend 整体复制代码和工程文件，再应用本项目 API/proxy、Docker 与文档导航差异；不手写“看起来相似”的组件版本。固定来源提交、保留来源 lockfile，校验文件哈希；记录集成例外和原因。

同步清单见 [frontend-source.json](../../../../scripts/frontend-source.json)。`python3 scripts/check_sources.py --frontend` 比较当前文件与同步收尾快照，列出未经记录的差异；清单是来源证据，不要求将后续业务代码回滚成模板。更新基线时重新审查例外，不能先删断言再宣称一致。

排除来源自身 docs、前端级 .codex/.claude、独立部署 Caddy/Railway、无关业务 HTML；不复制参考仓库其他目录。当前项目文档在 `docs/engineering/frontend` 按最终代码维护，frontend AGENTS 只导航。

安装、检查、开发与整栈启动见 [frontend README](../../../../frontend/README.md)。生产 API 不可用时不回退 mock；新能力先确认真实 backend 契约。公共 token、Theme、Provider、Router、组件只保留一份，不并行创建来源版和全栈版。
