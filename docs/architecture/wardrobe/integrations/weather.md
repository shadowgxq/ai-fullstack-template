# 城市与天气｜技术专项

关联：[总体方案](../overview.md) · [账户设置](../features/account-and-profile.md) · [穿搭推荐](../features/outfit-recommendation.md)

天气是推荐可选的**事实来源**，不是独立业务核心。它只负责确定可信城市、获取当天天气并说明数据时效；不能确定衣物搭配，也不能在天气失败时阻止无天气推荐。

## 1. 城市选择与地区映射

选择顺序：**用户本次有效手选/定位结果 → 已保存城市 → 默认杭州**。默认城市为 `浙江杭州 / 101210101`，展示时明确标注“默认杭州”，不得假装用户已经定位。定位失败或取消保留当前有效城市。

| 入口 | 处理流程 |
|---|---|
| 手选城市 | 小程序输入关键词 → Backend 获取候选并核验省、市及地区码 → 用户选中稳定 `city_id` |
| 用户主动定位 | `wx.getFuzzyLocation(GCJ-02)` → Backend 用腾讯位置服务逆地址解析到省市 → 匹配可信天气地区目录 |
| 无有效选择 | 读取 profile 已存城市，否则使用默认杭州；不自动索要位置权限 |

Backend 持有版本化 `weather_regions(region_id,weather_code,province,city,district?,aliases,geocoder_city_code?,mapping_version)`。同一地区的默认、手选、定位结果归一成相同 `region_id`；不直接将腾讯行政码截断成天气码，也不因为返回第一条城市搜索结果就认定有效。搜索展示完整省/市/区县层级以区分同名地区，景点、街道或多候选不明确时保留手选入口。

可信目录来自中国天气网[移动搜索页](https://m.weather.com.cn/city/citysearch.shtml?fromurl=index)实际使用的[公开搜索数据](https://i.tq121.com.cn/j/wap2016/news/city_search_data.js?2022042521)，并与其[PC 层级目录](https://j.i8tq.com/weather2020/search/city.js)核对。只解析受限数据字面量，不执行 JavaScript；只接纳天气码唯一、国内层级完整、两源名称与省份一致的条目。混合的国际/乡镇/景点、重复码、来源冲突或缺失条目不自动归一，旧名不凭经验补为别名。电话区号与邮编不能作为腾讯行政码。

经过核验的目录以冻结版本导入业务库，版本关联规范数据哈希及来源元数据；Last-Modified 仅作来源记录。`GET /cities` 搜索该版本的可信条目，其游标只分页这些实际命中，不冒称上游有全量行政区划分页。天气页仍须校验请求天气码与正文地区身份；目录一致不等于每次天气响应都有效。

模糊定位只在用户触发时调用，坐标仅供本次解析，不保存位置历史；小程序需核对 API 支持、授权、实际账号开通和隐私声明。基础微信登录不等于已有定位权限。

## 2. 天气数据获取与消费接口

使用 **中国天气网 HTTP 页面**与上述公开城市搜索数据。天气请求由 Backend 在固定域名/路径发起，不接 MCP、模型搜索或任意用户 URL。HTML/JSON 数据按版本化解析器提取，校验结构、地区身份、天气日期、观测时间及预报发布时间；不运行网页 JS，不从其它未证实字段凑天气事实。页面缺少有时刻证据的观测时保留 observation 缺失；有效当日预报可以单独返回，夜间和次日白天不能拼成当日实况或完整高低温。

| 接口（`/api/v1` 前缀） | 输入与返回 |
|---|---|
| `GET /cities?q=&cursor=` | 返回经校验的 `city_id / region_id / province / city` 和受限搜索结果；不虚构上游不存在的全量分页 |
| `POST /weather/context` | 可选 `city_id` 或模糊坐标（明确 `gcj02/fuzzy`），两者互斥；都没有时使用已保存/默认城市。返回账号归属的 `context_id`、地区、来源、天气状态与有效期 |

**个人上下文与公共缓存分离**：建议业务数据库维护 `weather_contexts(id, owner_id, region_id, selection_source, weather_date, valid_until, state, payload_snapshot?, missing_reason?, created_at)`。`context_id` 必须检验 owner 和有效期；Redis 的共享城市 key 不能作为个人授权凭据。取得天气时冻结必要来源事实，失败时也可产生标记 `missing` 的上下文，便于推荐沿同一接口继续执行。

推荐创建时复核 context 后将必要天气事实/缺失原因写入推荐冻结输入。运行中的 AI Run 不依赖 Redis 历史 key；已过期 context 不用于新的当日推荐。个人城市选择、坐标、历史和昵称不进入公共天气缓存。

公开的天气事实包含：地区/日期、来源与解析版本、抓取时间、`valid_until`，以及可缺失的 `observation(observed_at,temperature_c)` 和 `forecast(forecast_date,issued_at,day_summary,night_summary,high_c,low_c)`。**观测与预报分开标识**，页面展示原数据时间，不把当天早些时候的缓存称为实时天气；不能把预报最高温冒充观测温度。

## 3. UTC+8 Redis 日缓存

同一规范地区在同一 `Asia/Shanghai` 自然日共享一份天气快照，与穿着日期使用同一日界，不随客户端设备时区变化。当天午夜后旧数据不能作为新一天的天气使用；历史缓存保留 7 个自然日供有限排障。

- 缓存键：`weather:v1:{source}:{parser_version}:{region_id}:{YYYYMMDD}`。key 不包含账号、坐标及用户输入；`valid_until` 为查询日下一个上海时区 00:00。
- 首次请求未命中时，对同地区/日期用短期 `SET NX EX` 锁合并抓取；持锁者二次检查、抓取并校验后原子写入。非持锁者等候读缓存，超时则报告天气缺失，不并发大量抓取。
- 锁写入/释放按随机 token 及业务日复核；过期锁的旧抓取者或跨午夜响应不能覆盖新结果。缓存通过 `EXPIREAT` 在缓存日加 7 天的 00:00 清理。
- 上游暂时失败只使用短期负缓存（如约 60 秒，且不跨日），避免把一天锁死成无天气。Redis 失败时，已通过认证的天气请求可受限直连来源；**不能借缓存失败绕过现有 Redis 鉴权/撤销逻辑**。

日缓存降低调用量，但不保证当天实况随时刷新。若以后提出实时天气要求，需重新评估缓存有效性规则，而不是静默改动当前数据时效。

## 4. 异常、验证与生产条件

| 场景 | 必须得到的结果 |
|---|---|
| 拒绝定位、地图解析失败、同名城市不能唯一匹配 | 保留当前城市或手选；不猜测实际位置 |
| 天气请求超时、403、数据结构变化、日期不符 | 明确标记天气缺失，继续不依赖天气的推荐 |
| 观测缺失但有效预报存在 | 只展示有证据的预报，不伪称观测成功 |
| 跨日期或缓存锁竞争 | 昨日数据不能进入今日 key；失锁执行者不能覆盖新值 |
| 跨账号使用 context_id | 拒绝访问，公共天气共享不等于用户上下文共享 |

验证以冻结解析 fixture、隔离 Redis 并发/TTL/跨日测试、Backend context 归属与推荐降级测试为主。真实上线还需核验微信模糊定位权限、腾讯地图 Key 和域名，以及中国天气网的**生产使用条件**：已有 HTTP 解析样本只能证明技术可访问，不能代表已获内容使用许可。失败时不偷偷换数据源或编造结果。
