# Change 拆分与验收归属规则

## 四层对象不能混同

PRD requirement 是可观察行为；capability 是稳定业务能力；change 是一次有明确意图的差异；task 是实现步骤。
一个 change 可以覆盖多个 requirement 和 capability；前端/API/存储/测试通常是同一 change 的内部工作。

## 全文子句与归属

从需求全文提取规范性子句：业务规则、默认值、限制、状态、流程、权限、失败恢复、持久性、外部契约，以及正式验收。
同一句/列表项有多个可分别验证的结果就分拆；去重时保留所有源引用，不能丢限定条件。
一个 requirement 只有在目标与 owner 集合一致时才合并。每个 change 完成时必须能满足所有关联 acceptance。
上游修改影响未来页面时，上游只承担当前可观察保证；下游页面引入时承担其一致性要求。跨面保证保留，不能删掉，也不能让未来页面成为上游的虚假完成条件。
复用一个 requirement 时逐条审计每个消费者，不接受“各自负责自己的部分”这种未拆清的文字。
依赖只有显式 depends_on 算数，batch/wave 早晚不能替代真实依赖。

## 五项边界测试

1. 一个清晰意图，而不是“另外还要”拼接无关功能。
2. 产生可使用/观察的用户或系统结果，不只是给未来代码搭架子。
3. 在声明依赖完成后可独立验收，不借未来任务或假页面满足条件。
4. 单独评审、合并、归档与发布决策有意义；回滚需兼容策略，并不要求数据库破坏性操作可无损倒退。
5. 边界依据行为/契约/风险，不仅依据目录、技术层、角色或 Agent。

不满足独立结果和验收的，合并到消费它的 change 或成为 tasks.md 工作。

## 保持一起 / 允许拆开

同一用户事务、同一核心不变量、同一恢复闭环、串行技术脚手架优先一起。
独立目标、可推迟的完整子结果、单独迁移/安全/兼容性风险可拆。
技术地基只有可独立使用和测试的稳定契约、平台能力或风险边界才独立成 change；仅“可复用”不够。
超过约20–25个任务仅触发粒度检查，不能机械硬拆。即便只有5个任务，两个无关产品意图也应分开。

## 必须进行一次合并复核

检查每对依赖与相邻 wave：上游能独立验收吗？只是分了技术层吗？是否共同完成一条路径？
合并能否消除重复方案和跨 change 不变量？如果是同一逻辑单元则合并。合并后再次检查是否混入无关目标。

## 并行不是产品拆分理由

先形成合理 change，再在 change 内用任务 DAG 并行实现。
契约先就绪后，前后端可以并行；不是所有项目必须后端全做完才能开始前端。
写入、读取、共享类型、路由、配置、国际化、数据库、端口及浏览器状态都要检查冲突。

## 显式输入台账

执行 [输入边界与共享引用](input-contract.md)：来源先分类、公共定义再提升、消费者显式引用。
“下游输入”标题只提供候选，不使项目规范或源码入口自动变成 Input。真正资源的子项独立核对；同一消费视图的章节用一个 scope 列表，不逐章拆 Input。
候选台账完整指每项都有分类及去向，不要求每项写进 inputs。规范读取走 AGENTS，既有 PRD/技术/UI 来源用专用字段。
公共资料在顶层 inputs 定义一次，input_refs 只给实际消费者；不同 scope/required/snapshot 不自动合并。
运行前验证有效输入可读性，缺必需输入不启动；可选缺失显式披露。远程输入用真实工具取得 snapshot。
新计划必须通过 validate --strict-inputs，并核对展开后的消费范围，不以去重数量代替语义审查。

## 规划深度与执行窗口

按[规划策略](planning-strategy.md)解析用户/项目偏好，再由 AI 根据实际不确定性判断。明确范围可以一次规划多个 Batch；探索部分滚动细化，混合项目不机械只留首批。
一个 batch 是可验收里程碑；只为当前执行的 Change 生成必要 artifacts，详细计划与同时在制品数不是一回事。
批次 checkpoint 独立于规划模式，只有受授权且检查有效的 auto 批次才能连续推进；人工裁决与规划边界不自动跨越。
状态和日志不进 PRD；覆盖证据外置。下一批已经规划且条件未变时直接执行；只有未排期或目标发生变化才再次规划/修订。
