# 设计与实现工作流

本页是设计阶段、代表页验收和职责的唯一规则源；[Manager 工作流](MANAGER-WORKFLOW.md)维护阶段调度、代码状态与产品验收。四个设计 Skill 只补各自动作，不运行第二套计划。

## 执行范围

完整交付中的唯一顺序是：**确认 PRD → UI/UX 设计交付 → 正式技术方案 → OpenSpec 规划 → 按任务实现 → 还原与产品验收**。Manager 阶段调度见 [Manager 工作流](MANAGER-WORKFLOW.md)，输入绑定见 [Manager 接入](ui-ux-delivery/references/manager-integration.md)。

UI/UX 不拆成两轮原型或两套稿。`ui-ux-delivery` 将当前已确认需求整理成设计任务，`pencil-design` 通过真实设计工具完成可编辑稿、必要状态、保存回读与渲染检查；只写任务说明不等于设计交付。设计前核对现有架构、组件/API、Token、平台及数据/权限边界，只做必要可行性检查，不另写一份前置技术方案。

**当前已确认需求范围完整制稿，代码按 Change / task IDs 实现。** 设计范围不是未来整个产品，也不按尚未生成的 M/Change 切断同一次设计交付；大型探索需求先确认本次可独立设计的范围。制稿不授权创建 OpenSpec 制品或业务代码，PRD 仍只描述产品，不混入实现计划。

| 当前范围 | 处理 |
|---|---|
| 新页面、布局骨架/导航/信息层级或关键交互变化 | 正式技术方案前完成当前范围的 UI/UX 设计交付；需要时局部修订既有稿 |
| 已有适用设计稿 | 核对版本、范围、必要状态、实际检查与接受记录后复用同一来源，不重复制稿；有缺口只补相关部分 |
| 文案、小型修复、不改变结构和关键交互的样式修正 | 沿用项目规范定向修改和验证，不新增完整制稿或代表页确认 |
| 无 UI 影响 | 不生成设计任务/Pen，不阻塞其技术方案与普通实现 |

直接调用技术方案、规划或 Execute 也核对本阶段前提；缺项返回对应准备步骤，不默默降级成“执行时再设计”。只请求设计、文档、实现或验证时，到本次授权终点返回原协调者，不自动取得后续阶段权限。Skill 是给当前 Agent 的指令，不是自动调用引擎；协调者必须实际加载入口及可用工具。

## 各层职责

| 来源 | 唯一维护内容 |
|---|---|
| PRD / OpenSpec specs | 产品目标、业务/权限规则、用户动作与可观察结果；Pen 不改变这些规则 |
| 项目设计/工程规范与源码 | 视觉政策、正式 Token 值源、组件治理和当前可调用 API |
| 需求级设计记录 | 当前范围的 UI 设计任务、来源/状态覆盖、接受决定及交接；按项目设计文档导航定位，缺少位置时才在设计目录新增一份 |
| Pen 库与消费稿 | 变量、公共组件、页面实例、布局、变体和视觉状态；业务行为引用 PRD/specs |
| 技术方案 | 读取 PRD 与真实设计，确定数据/API/状态/权限等实现契约，引用设计记录，不抄设计正文 |
| OpenSpec `design.md` | 当前 Change 技术决定及 **UI 实现依据**：设计记录/修订、Frame、状态和本任务适配；保留技术方案其他章节，不复制上游 UI 设计任务 |
| OpenSpec `tasks.md` | 唯一实现任务清单，UI 条目明确 `design-to-code` 的范围；由原协调者按真实结果回写 |
| 四个设计 Skill | 需求到设计交付、制稿、任务内实现、验证；不维护平行任务或批准系统 |

设计开始时尚无 Change，使用需求来源和当前范围定位，不要求 Change/task IDs。设计任务与最终交接更新在同一份需求级设计记录中，后续阶段引用它；仅一次性文档任务可直接回复，但正式后续工作须有项目内可持久引用的来源。不复制 PRD、组件清单或 Token 值表。

具体布局、排版、配色和组件组合由 pen.dev 在项目约束内决定；用户参考图默认可选：有图就实际读取，无图/不可读则说明后依已有规范继续。仅明确必需或精确复刻的来源缺失才阻塞依赖步骤；迟到参考先判断影响，不自动推翻已接受结果。

## 代表页与页面同步

新建或实质改变共用视觉方向时，先展示一个覆盖核心任务的重要代表页。已有同范围、仍有效的真实接受直接复用；单页任务不增加其他页面，也不逐状态签字。

1. 实际完成代表页的可编辑设计、必要状态、保存回读和渲染检查，交付真实文件/Frame、修订、主题/视口/状态，以及入口 → 动作 → 预期结果。
2. 前期验收对象是设计稿，不以尚未实现的业务页面作为设计接受前提；浏览器中的实现效果属于后续还原与产品验收，不在设计阶段偷跑业务代码或用 Pen 截图冒充运行结果。
3. 引用真实反馈，记录版本、接受范围和异议；沉默、超时、MCP 成功、自评或仅认可配色不是整页接受。用户明确指定现稿为目标时记录该指令，不捏造历史验收。
4. 接受后复用变量、真实组件实例和布局方向，完成当前已确认需求内其余页面及必要状态。各页仍须检查，不继承代表页的 passed；完成范围不能只停在代表页。
5. 等待只阻塞依赖该决定的设计扩展，继续已授权且可独立的调查/检查。退回只修相关部分，不更换入口绕过；设计方向与最终产品效果分开记录。

设计接受不代填产品 `human_acceptance=accepted`；它与后续真实产品验收不是同一对象。同一对象已有有效的同一反馈，不要求用户重复确认。

## 设计就绪与技术反馈

进入受影响的正式技术方案前，核对：当前 PRD 对应的页面/交互/必要状态均有表达；目标可编辑稿已保存并回读；项目要求的主题/视口与渲染已实际检查；必要代表页决定有效；没有妨碍交互确定的未决产品问题。技术假设记录边界与待验证项，交正式技术方案验证，不要求制稿前完成正式技术方案；已知不可行且影响设计方向的风险应先解决。已有稿按同一条件复用，纯后端和轻量修改按前述范围判断。

文件存在、截图存在、文档写完或工具连接成功不构成就绪。缺 MCP/必要来源/有效接受时标注具体 `not_run` 或阻塞；不能用解析测试、模拟图、静态夹具或自评宣称真实制稿完成。仅调查假设可继续，不将受影响方案定稿、将该范围排成就绪计划或开始 UI 实现。

技术方案必须实际读取 PRD、设计记录和相应 Pen 节点/状态，不能只抄路径。发现不可行交互、缺少权限/失败路径或契约冲突时，按“问题 → 影响 → 最小调整”返回原设计协调者；局部调整沿用同一稿，不生成另一轮 UX/UI。产品行为变化先确认并更新 PRD，再修设计、技术方案与受影响计划；同一颜色/布局的小修不触发全局重批。

正式技术方案与已确认设计一致后才进入规划。规划/执行中发现实质缺口或来源变化，回同一设计—技术反馈链，只使受影响决定、引用和验证失效；已存在计划由 `manager-revise-plan` 更新真实消费者，无计划时不先建一个计划来修设计。设计修改需明确授权，不能改正确设计/Spec 来掩盖代码缺陷。

## 共同读取协议

同一任务已读且未变化的依据可复用；只读取当前影响范围。

1. 确认授权、任务/目标包、实际平台与宿主、页面/区域、状态、保留项；读取为理解宿主可覆盖整页，写入不得因此扩大。
2. 沿实际 AGENTS / 项目导航读取必要设计、组件、Token、状态/可访问性、业务与运行规则。路径存在不等于已读；关键规则不可访问时报告具体缺项，仅继续不依赖它的工作。
3. 从清单定位后核对真实 export、props/事件/状态拥有者和必要调用点。按项目治理复用/组合/必要新增，不按设计图层数创建组件，不凭同名推断 API。
4. 从正式值源核对本次语义 Token、主题、单位、别名与有效值。同值不等于同用途；控件内部样式通过真实组件契约消费。不默认导出全量色板或建立平行值表。
5. 通过当前来源能力读取真实文档/节点、结构、样式/变量、实例、资产和必要基准图，区分保存版、编辑器版与读取失败；无稿不创建假快照。
6. 核对业务含义、状态、组件职责、Token 语义和页面/应用壳/系统宿主的归属；按 [组件归属与主题表达](#组件归属与主题表达) 区分维护源、展示与验证，按 [冲突与缺口](#冲突与缺口) 处理差异，再在任务范围执行和验证。

## 组件归属与主题表达

优先采用项目已确认的治理规则。缺少明确政策时，默认精简公共设计系统：保留 Tokens、基础 UI 与具有稳定、无业务依赖契约的通用交互；复杂组合、业务布局和通用性未明确的组件先留业务。Dialog、Tabs 等可以是组合组件，公共准入不以原子化程度决定。

结合真实设计、源码、状态拥有者及调用点判断，不能只因跨页使用、外观相似、可替换文案、已有 shared 实现或 `reusable` 标记就提升为公共。设计主组件与代码组件不要求一一对应；业务模块的公开出口不等于公共设计系统成员，设计归属调整不自动触发代码搬迁或重复实现。

项目没有既定组织时，默认一个公共设计库与一个业务消费稿，沿用项目实际文件名；业务稿可维护自己的可复用主组件。既有文件组织、额外文档和导入关系先按实际用途判断，不为了默认数量擅自建文件、合并或迁移。

对明确支持 Light / Dark 的项目，默认一份组件/页面结构、同名语义的两套主题值；其他主题集合以项目声明为准。未变化的几何与交互共用，不创建独立主题主组件或为每个页面、状态、宽度强制复制画板。普通页面可通过主题切换核验；紧凑的颜色配对板、关键状态及评审需要可用同源实例或截图展示。图片/Logo、图表、渐变、透明叠层、阴影/边框或真实结构差异需要额外表达时，记录局部差异并共用其余结构。

展示精简不减少项目要求的主题验证。核对受影响对象在支持主题下的有效值、实例覆盖和渲染；基础契约证据可在未变化时复用，页面独有组合仍需检查。Token 绑定不能证明对比度、透明合成或资产适配正确，也不能把代表样例的结果套给未检查页面。区分已查看的主题/状态与 `not_run`；只读任务不切主题、不保存，文档任务不自动清理画布或历史证据。

## 冲突与缺口

按“规则来源 → 当前事实 → 本次处理”记录。源码决定当前可调用 API，不证明它符合目标规则；设计决定授权内目标视觉，不授权改业务/公共 API/正式 Token。需要变更这些来源时回到其实际拥有者及当前需求范围；已有 Change 时同步受影响消费者，不通过改正确规范掩盖实现错误。

没有项目政策时才采用现有一致性、最小组合与就近实现。公共库修改检查直接消费者、主题和覆盖；未读部分留为未验证。缺少映射可在授权内补最小表达，不扩建完整库；新增跨任务影响先调整真实依赖和写入范围。

## 验证与重试

在现有报告分别记录设计结构、`code_checks`、`runtime_checks`、`visual_checks` 的实际范围及 `passed | failed | not_run`。代码/Lint、结构解析、截图采集、真实交互和用户接受不能互相替代；有截图还须实际比较，Web/mock 不证明原生或真实后端。

有稿比较固定来源修订、目标/状态/主题、平台、逻辑尺寸和已批准适配。局部任务检查受影响区域及必要宿主集成，不因此验证/重写无关整页；缺基线可检查项目规则，但不声称设计还原通过。受影响源码/Token/API/条件变化后旧检查失效，按 [缓存合同](design-to-code/references/cache-contract.md)核对绑定，只复验受影响部分。

检查命令从实际项目读取。普通 Manager Change 不新增浏览器硬门禁；运行与视觉检查按本次授权在实际验收位置进行，已明确要求的必要检查不得省略或标通过。QA 默认只验证，修复由原实现者在其范围内完成，不修改源稿迎合错误代码。

恢复先读当前制品、实际文档状态、任务与有效决定，只补未完成部分。无新证据时不重复无效命令，沿调用方预算与重试规则处理；缺能力/关键输入/权限时停止依赖步骤、保留现场并继续独立工作，不换入口绕过停点。

## 最小交接

设计阶段复用需求级设计记录，技术/Change 阶段引用该记录；实现与验证复用 `verify-report.md` 或当前回复，不新建平行 intake/plan/report/status 文件。

| 内容 | 记录范围 |
|---|---|
| 任务 | 需求来源/范围；实现阶段追加当前 Change / task IDs，目标页面/区域/状态、读写边界与保留项 |
| 依据 | 已读的规范/源码/设计版本、真实文档与 Frame、必要共享库 |
| 映射 | 关键实例/变体 → 实际组件 props/事件/状态 → 正式 Token 语义；数值只作为本次解析证据 |
| 决定与结果 | 代表页实际接受及适用范围、已执行检查与证据、缺项和待恢复位置 |

## 来源安装与读取

相关 Skill、共同文档和脚本使用同一仓库提交的完整依赖，保留相对目录关系；实际路径、版本和内容必须可读。分别记录仓库分支/SHA、项目锁定包来源/摘要及实际加载路径/内容标识；版本号相同不能代替内容核对。

更新时整体替换受影响安装目录及共同依赖，再按客户端机制重新加载和检查引用，避免覆盖式安装留下多余入口。项目只维护项目规则和资产，不复制通用规则作为另一维护源。升级不修改用户业务代码、项目资料或验收记录。

Pencil 内置 AI 选用实际导入的 `pencil-design`；导入不证明项目原文件已加载。自定义菜单 Skill 与 MCP 的 `read_skill` 操作说明不是同一来源；工具及参数从当前安装发现。客户端不可用就报告未执行，不用静态/协议夹具冒充真实制稿。
