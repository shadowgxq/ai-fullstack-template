# 代码与逻辑验收

## 单 Change

核对需求代码条目、真实 diff、适用的公共契约和项目现有规范，选择能证明当前行为的最小检查；不按角色轮番复检。

| 影响 | 检查 |
| --- | --- |
| 文档/非运行时配置 | diff、引用、格式或配置解析；不默认构建/跑全库测试 |
| 函数/API/状态逻辑 | 正常、边界、错误、权限路径；相关单测/契约/API 检查 |
| 持久化/SQL/迁移 | schema 与方言、索引/查询、数据一致性；确有需要才用明确授权的隔离库验证 |
| UI 代码 | 项目已有 token、公共组件复用、props/状态/事件绑定、loading/empty/error/disabled 处理，明显布局与语义错误的静态检查 |

检查 token/组件时引用项目真实定义；不存在规范则按现有一致性判断，不自创禁止硬编码或强制新组件的要求。纯颜色/间距改动不用机械要求业务单测；涉及逻辑仍需对应测试。
不以 .tsx/.css 等后缀直接触发浏览器。静态代码只能发现可从源码确认的问题，不能证明没有按钮重叠、裁切、响应式问题或真实交互缺陷。
类型、Lint 和测试失败先判断实际影响，不把它们一律称为非关键。既有失败也需证明与本次无关，分别记录；必需逻辑验证未运行时不能标为通过。

## 阶段与人工

阶段检查由 Execute 收尾，无论它由用户直接调用还是由 Run 调用：补查本阶段引入的跨 Change API、数据和代码集成保证，全部成员与必要阶段检查通过后才回写阶段 code-verified。Run 只消费结果，不重复检查；已通过且相关代码/环境未变的结果复用。必要真实数据库验证未完成，相关阶段仍未代码验收；不将浏览器缺失误判为代码检查失败。
视觉、交互体验、可用性与产品效果由用户在 Plan 明确位置验收。交付入口/操作路径、预期结果、已知风险，不生成假的截图/验收记录。多个 UI Change 合并为一份阶段人工清单；前期代表页的设计接受只证明相应设计决定，不替代实际运行与产品体验。
本次已授权浏览器协助时，协调者按相应范围单独组织 design-qa/实际操作取证；没有真实反馈仍不能标记产品已接受。这不是普通代码执行阶段的默认步骤，也不扩成逐 Change 门禁。项目已有相冲突的强制浏览器规则一次报告，请用户决定验证安排，不静默覆盖项目规则。

## 简短报告

每个 Change 的 verify-report.md 仅写：本次范围/相关版本、检查项与命令结果、独立审查结果（省略或未完成时注明）、静态 UI 发现、剩余逻辑阻塞、人工待验和修复尝试。原生终端日志能引用就不复制；无需单独生成 snapshot、Review JSON 或签字凭据。
实现变化只复验受影响逻辑及消费者；不因无关文件、参考资料或格式变化要求全量重验/重新人工批准。源码结论必须有路径，真实执行结果必须来自工具；自查明确称自查。

## UI/UX 参考防偏移

按[接入契约](../../ui-ux-delivery/references/manager-integration.md)读取当前 design/contextFiles 中的 Markdown 与 Pen 目标，在源码层核对用户任务、输入输出、保留项和变化：业务选择是否退化为普通用户手填内部模型，既有路由/数据/权限是否被视觉改造改变。扩展页面核对代表页接受的版本与范围；这项设计决定不能代写代码或产品通过。只报告可从源码证实的结论；静态 Pen、Mock、文件齐备不证明实际运行、视觉或交互通过，未执行保留 not_run。合理适配按项目规则及实际接受范围处理，必要真实体验检查仍在已安排的独立产品验收中。
