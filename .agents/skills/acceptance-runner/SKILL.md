# Acceptance Runner

**核对批准 → 准备 → 执行 / 取证 → 分流 → 授权修复 → 保存 → 复测 → 报告。**

这是指令型本地工作流，不是常驻运行器。工具实际不可用就报告；不得模拟执行或使用不存在的 API / CLI。

先读项目 AGENTS.md、指定 `qa/<scope>/acceptance.md` / `plan.yaml`，以及本 Skill 的 [运行协议](references/execution-contract.md)。按需使用 [状态模板](assets/state.json) 和 [报告模板](assets/report.md)。所有项目路径相对被测项目根目录。

## 1. 批准、授权与恢复

确认用户已明确审核本轮标准、计划与待确认问题。无真实确认就停在 awaiting_review，不修改模板假装 approved。

记录实际确认引用、标准与计划的 SHA-256、输入文件摘要；核对需求未发生未批准变动。摘要不能证明身份，只有真实用户消息 / 宿主批准是授权依据。测试、测试钩子、业务修复、Repair 登记和 Git / PR 发布分别核实授权。

继续任务先读取原 state，核对旧写入者 / 进程已停止、HEAD / 差异 / 运行服务版本、已发生的 Git 和数据副作用。复用 run 与问题 ID、累计预算；不直接重新创建一轮以清零。归属或预算无法确认时暂停修复。

新 run 使用不重复的时间戳加短随机后缀，创建 `qa/<scope>/runs/<run-id>/`。记录初始 HEAD 和已有改动；默认要求干净的代码工作区，已有用户修改不 reset / stash / 覆盖，也不擅自一并提交。无法分离时由用户处理或批准隔离方案。

## 2. Preflight 与 Prepare

核对 YAML 结构、必测覆盖、ID 唯一、依赖完整无环；核实命令、实际工具、允许域名 / 账号、数据准备、就绪状态和服务版本。空配置不能默认为成功。

优先复用已有 Playwright 依赖 / fixture / 配置；只在批准的测试和支持文件中生成缺少的脚本，保证标题与 TC ID 对应且可被测试发现。准备测试不得偷偷改变验收或核心断言。

Playwright 页面定位先用 role / label / 文本 / 作用域。只有计划已认定“适合增加最小测试钩子”时，才在 `testability_files` 内加稳定 `data-testid`；默认空则无权改页面。**计划为 `computer_use_chrome` 的场景不为了测试去补 testid。** 如果运行时才发现原 Playwright 场景不适合加钩子，标 `needs_review` 并建议改计划，不能擅自侵入页面或静默换执行器。

按计划准备隔离数据；重复运行必须查询或复用本 run 的数据，不重复制造不可识别数据。仅管理本轮启动的服务。实际缺失能力影响哪些用例，就阻塞哪些；不将其标通过或静默换执行器。

准备完成的测试代码已获发布授权时，由本外层检查差异并形成远端检查点，不等待完整验收才保存。

## 3. 按计划执行并取证

串行执行先决已通过的用例。执行前记 running、操作意图与代码版本；执行后写实际结果和证据。原子写 state：先写同目录临时文件，成功后替换；一个主会话写状态。

- Playwright：调用已核实的测试命令，记录实际被发现 / 执行的用例、断言、退出码和必要截图 / trace。0 tests、skip、超时、命令未执行都不能算通过。
- Computer Use @ Chrome：确认 Codex 当前会话实际可用 Computer Use 的 Chrome 入口后操作，只访问批准来源；记录动作、实际观察与证据。不能用截图声称已读取 network / console；缺必需证据则 blocked。
- 保持测试 oracle：结果与已批准标准比较，不能根据当前错误实现修改预期。没有客观 / 已批准视觉基线的个人判断列为 needs_review，不直接自动修设计。

网络 / 工具瞬时错误只按预算有限重试；保留首次失败。不要通过反复重跑直到绿灯掩盖不稳定行为。

## 4. 失败归因与上游交接

先区分业务缺陷、测试实现错误、环境阻塞、需求歧义 / 新偏好；没有复现或明确证据不做猜测性业务修改。

测试实现错误只修已批准测试路径，不改变标准或删断言。活动 Change 业务缺陷交 `$manager-bugfix`；独立存量缺陷在用户明确授权后使用 `$repair-intake` 登记并交 `$repair-runner`。已有关联项复用，不新起另一队列并行修。

调用前读目标项目实际安装的 Skill 与项目约定；缺入口或 repairs 约定就记录阻塞，不自动初始化 / 复制上游。不替上游修改控制状态、不绕过其 Review / gate。需求或设计变化回上游评审。

只有低风险、可复现且允许路径明确时执行已授权修复；最多 2 轮含首次，与上游剩余预算取更严格者，跨恢复持久化。同根因只在证据支持时关联，不能换 ID 重置次数。

## 5. 外层保存与复测

现有修复 Skill 不执行 Git；待其交回控制权，由本验收外层做发布。本方案不假设存在未实现的中途回调。上游必要检查照常完成，返回后不等待验收层回归才保存改动。

每次检查点：核实仓库 / base / head / 既有 PR、用户授权、Diff 文件归属和敏感信息；仅显式选择本轮允许且已完成的文件 commit + push。上游合法维护的元数据逐文件核对其来源；不得顺带提交无关队列或其他人的暂存内容。

优先更新既有 PR；没有才查询同 head 是否已有 PR，再创建 Draft PR。保存远端 SHA、PR 编号和验证未完成项。发布失败仍保留本地代码和错误记录，不删除工作；恢复先查远端是否已成功，避免重复。

即使上游返回 blocked，只要改动可安全归属且发布已授权，也可保存为未验证草稿；不能标已修复。没有可提交差异就不创建空 PR。

随后在当前代码重新执行原失败用例和实际受影响回归；重复的同版本检查可引用真实证据，不要求两层各跑全套。Manager 的独立 Review / 完整 gate 或 Repair 必要检查不能被本层替代。

相关代码再变化使证据失效时重验受影响项。仍失败且预算允许继续同一问题；否则停止修复并给出明确阻塞。不能因本层测试通过自行把 Repair 标 verified、推进 Manager、归档或合并 PR。

## 6. 清理与结果

在安全边界按用例 / 计划清理本轮数据，核实结果；只停本轮进程。清理失败记录实际残留与风险，影响隔离时不继续后续项。

报告分别给出用例通过 / 失败 / 阻塞 / 待确认、必测覆盖、真实检查、未验证项、缺陷引用、代码保存和 PR 状态。必测全部通过且必要门禁满足才是 pass；必测缺证据为 incomplete，不能用总体“完成”掩盖。

保留原始本地证据；PR 只包含脱敏摘要或已获共享授权的证据。预算耗尽、会话中断或工具不可用时保存可恢复状态，不承诺后台继续运行。
