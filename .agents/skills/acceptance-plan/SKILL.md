# Acceptance Plan

**读需求 → 澄清预期 → 规划用例 / 执行器 → 定范围 → 等待人工 Review。**

## 输入与约定

所有项目路径相对被测项目根目录。先读项目 AGENTS.md、用户指定需求全文、当前 Change 的场景及相关项目规范；按需读取 Manager 归属、已有测试、package 配置和最少相关源码。

不要把当前实现当成验收标准，不要全仓泛读替代定向理解。资料缺失则说明缺项，不能据标题猜测未读内容。

本 Skill 内的 [标准模板](assets/acceptance.md) 和 [计划模板](assets/plan.yaml) 是起点。模板示例不是目标项目的真实需求、路径、授权或验证结果。

## 1. 生成验收标准

为每个确定的可观察行为分配稳定 `AC-xxx`，写明需求来源、前置条件、操作与预期。复用已有 OpenSpec 场景的含义，不另行创造相反要求。

明确区分：已确认行为、阻塞本轮的产品问题、非必需建议。保存范围、权限、错误恢复、数据持久化等存在歧义时列出问题，不擅自选一种然后标“已确认”。

写 `qa/<scope>/acceptance.md`。标准只保留一份；plan 用 ID / 路径引用，不再复制全文需求或额外生成一份重复测试用例文档。

## 2. 生成用例并决定执行器

默认先评估 `playwright`：已有稳定语义定位且结果可编码时使用；缺少定位时，仅当增加极少量 `data-testid` 合理、低侵入且有长期回归价值，才继续选择 Playwright。**不适合增加 testid 的交互统一使用 `computer_use_chrome`**，由 Codex Computer Use @ Chrome 按真实 UI 路径执行。可以为同一标准拆出两个关联用例，分别验证可编码结果和真实 UI，不创建 hybrid 引擎。

每条用例写：ID、标准引用、必要前置 / 数据、步骤、执行器及选择原因、必需工具能力、是否必测、证据、清理。既有测试可直接引用；没有脚本就指定未来测试文件与唯一标题，留给 Runner 生成。

可选 `depends_on` 只用稳定用例 ID，先决项应排在前面；不能成环或引用缺项。优先独立用例，避免测试间共享可变数据。每个必测标准至少有一个必测用例覆盖。

先检查已有 role / label / 文本及作用域。若没有稳定定位，再判断最小测试钩子是否适合：适合则把具体 `testability_files` 纳入 Review，Runner 后续写入；**不适合则直接规划 `computer_use_chrome`，不要为了 Playwright 强加 testid。** 执行器选择属于计划，运行时缺能力标 blocked；若需改变执行器，回到轻量 Review，不能静默切换来凑通过。

## 3. 最小执行准备与写入范围

写 `qa/<scope>/plan.yaml`：真实项目来源、环境地址、版本识别方法、数据准备 / 清理、实际命令、用例、预算、允许写入路径以及目标仓库 / 分支 / PR 策略。

复用已有环境与 Playwright。新增依赖或配置也须列入批准路径；不要添加测试 SDK、全站 ID、平台或 CI。`testability_files` 默认空，表示不允许改页面；补定位钩子必须有具体需要和路径。修复允许区与测试允许区分开。

必须读取实际 package / 工具帮助后写命令；不存在的命令留待配置并说明阻塞，不虚构脚本。无需执行的 seed / cleanup 等明确写原因。不得把账号密码、Cookie、token 或生产连接串写进计划。

对存在 Manager / Repair 的项目，确认已安装入口和项目约定；只引用原路径和 ID，不修改其计划或队列。本 Skill 不负责安装、初始化或重设计 Repair。

## 4. Review 与输出

输出两个文件路径，以及精简摘要：必测范围、执行器分配、仍需决定的事项、预计代码改动和副作用、修复 / 发布授权范围。

不因为用户让“自动生成计划”就把它标 approved。只有用户明确确认具体内容，Runner 才可记录真实确认引用及标准 / 计划 / 输入内容摘要；用户可以修改草稿后再启动。

到此停止。不要启动服务、运行用例、登记缺陷、提交业务修复或调用 Runner。后续用户明确批准并要求执行，再进入 `$acceptance-runner`。
